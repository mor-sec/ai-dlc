# 05 — Rapid Prototyping

Prototyping under AI-DLC has a distinct purpose: **answer a business or technical question with a working artifact in days, cheaply enough to throw away**. Snowflake is our primary platform because our data already lives there; this chapter gives the Snowflake-first path, the alternatives, and — critically — the discipline for promoting (or killing) prototypes.

## Prototyping principles

1. **A prototype answers a question.** Write the question down in the Unit of Work before building ("Would ops actually use a queue-priority dashboard?"). No question, no prototype.
2. **Data gravity decides the platform.** Prototype where the data is — moving data is the slowest, most compliance-laden step. This is why Snowflake is our default.
3. **Prototypes are Bolts.** Same rituals, same plan gate, lighter Definition of Done: security scanning and data governance still apply (real data is real data); polish, scale, and full test pyramids don't.
4. **Label it.** Repo topic `prototype`, banner in the app, `PROTOTYPE.md` stating the question, owner, and review-by date. Untracked prototypes become unowned production systems — the most expensive artifact in enterprise IT.

## The Snowflake-first path

Everything runs inside Snowflake's security perimeter: no data movement, existing RBAC and masking policies apply, nothing to host.

| Building block | Use for |
|---|---|
| **Streamlit in Snowflake** | The UI in pure Python — dashboards, internal tools, approval flows. An agent generates a usable app from a schema + question in one Bolt. |
| **Snowpark** (Python/Java/Scala) | Transformations and ML in-platform, replacing "export to notebook" workflows. |
| **Cortex AI** (SQL functions, Cortex Analyst, Cortex Search, Cortex Agents) | LLM features on governed data — summarization, classification, natural-language-to-SQL, RAG over documents — without standing up any ML infra. |
| **Streams & Tasks / Dynamic Tables** | Event-ish pipelines inside Snowflake; the prototype analog of the event backbone in [Chapter 04](04-architecture.md). |
| **Snowpark Container Services** | Anything that needs a real container — custom runtimes, GPUs, existing images — still inside the perimeter. |
| **Native App Framework** | When the prototype's answer is "yes, and other teams/accounts want it" — packaging for distribution. |

**The default prototype stack:** Streamlit UI + Snowpark logic + Cortex for the AI features, generated by Claude Code from the Unit of Work, deployed the same day. The agent should use MCP access to Snowflake ([Chapter 03](03-tooling-strategy.md)) to introspect real schemas rather than hallucinate columns.

Limits to respect: Streamlit in Snowflake trails OSS Streamlit in version/features, compute-per-viewer costs need a warehouse-sizing sanity check, and a Streamlit app is not a customer-facing product surface. Hitting these limits is a *promotion signal*, not a reason to fight the platform.

## Alternatives (and when they beat Snowflake)

| Platform | Choose when | Notes |
|---|---|---|
| **Supabase + Vercel/Next.js** | Customer-facing UX, auth flows, real-time interactivity | Postgres + auth + realtime out of the box; the fastest path for product-shaped prototypes. Keep governed data out, or sync an approved extract. |
| **AWS serverless** (Lambda, API Gateway, DynamoDB/Aurora Serverless, Step Functions, Amplify) | The prototype must exercise the *target production architecture* — event flows, IAM, integration seams | Highest fidelity to production; slower first mile. Often the second prototype, validating shape rather than value. |
| **Databricks** (Apps, notebooks, Mosaic AI) | Heavy ML/feature-engineering questions, or the data is already in the lakehouse | Same data-gravity logic as Snowflake, different gravity well. |
| **Local + Claude Code artifacts/scaffold** | Pure UX concept tests with fake data, hours-long lifespan | Zero infra; nothing real to secure; dies by design. |

Decision heuristic, in order: **Where is the data? Who touches it (internal/external)? Does the question need production-shaped infrastructure?** First answer usually decides.

## Prototype → production: the gate

A prototype's Bolt ends with a **decision, not a drift**: kill, keep-as-tool, or promote.

- **Kill** (the common, good outcome): archive the repo, write one paragraph of findings into the Unit of Work. The question was answered; that was the point.
- **Keep-as-tool**: internal utility, explicitly owned, on the maintenance list, still labeled non-production.
- **Promote**: opens a *new* set of Units of Work — promotion is a rebuild against production standards, not a `git mv`. The prototype's value was the validated answer and the domain learning, and (uniquely under AI-DLC) its code regenerates cheaply against full standards. Promotion criteria checklist:
  - [ ] Question answered with evidence (usage, stakeholder sign-off)
  - [ ] Bounded context and event contracts defined ([Chapter 04](04-architecture.md))
  - [ ] Full Definition of Done applies ([Chapter 02](02-ways-of-working.md)): test pyramid, threat model ([Chapter 06](06-security-shift-left.md)), IaC + pipeline ([Chapter 07](07-devops-automation.md))
  - [ ] Ownership, SLOs, and run cost accepted by the owning pod

## Anti-patterns

- **The immortal prototype.** No review-by date, quietly load-bearing within a quarter. The `PROTOTYPE.md` review date and a monthly sweep are the vaccine.
- **Prototyping the whole product.** Six-week "prototypes" are just unmanaged projects. If the question can't be answered in ≤3 Bolts, decompose it.
- **Fake-data theater.** Demos on synthetic data that governed real data can never reproduce. Prototype on governed real data (that's the whole Snowflake argument) or state loudly that the demo is fiction.
- **Fighting the platform.** Hacking around Streamlit's limits with iframe contortions instead of reading the promotion signal.
- **Security exemption creep.** "It's just a prototype" never exempts real data from masking policies, secrets handling, or scanning. Lighter DoD ≠ no DoD.

## Tips & tricks

- **Schema-first prompting:** have the agent pull live `INFORMATION_SCHEMA` before generating; hallucinated columns are the #1 prototype bug.
- **Build a `snowflake-prototype` skill** ([Chapter 03](03-tooling-strategy.md)): scaffolds the Streamlit app, role grants, warehouse config, `PROTOTYPE.md`, and repo labeling in one shot.
- **Give every prototype a demo script** (five steps in the README). Prototypes exist to be shown; a demo that needs its author present answers nothing.
- **Track cost per question:** warehouse credits + agent tokens per answered prototype question — it makes the "kill" outcome visibly cheap and the immortal prototype visibly expensive.
